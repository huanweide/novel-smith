# Novel Smith 项目升级计划（2026-09-08）

> 基于完整通读 `README.md` / `README_EN.md` / `agent.md` / `ROADMAP.md` / `package.json` / `.env.example` /
> `prisma/schema.prisma`（27 个 model）/ 12 个页面 / 130+ API 路由 / `src/core` 30+ 模块后的产出。
> 目标只有一个：**提升 Star 数与真实用户好感度**。一切不服务于这个目标的改动（依赖升级、纯重构、版本号堆叠）全部剔除。

## 一、我对项目的理解（复述）

### 1. 它解决什么问题

写长篇小说的痛点不在"开头"，而在**中途失忆与后期失控**：写到 30+ 章 AI 开始忘设定、伏笔埋了不收、
角色人设前后打架、导出给编辑的排版一团糟、想不出新剧情。Novel Smith 的定位是——
把这些"脏活累活记不住的活"交给工具管，作者只负责创意和落笔。

它的核心叙事是**闭环**，不是单点生成器：
`一句话灵感 → 探讨模式聊出世界观 → 自动填表建档（角色卡/世界书）→ 批量写章（先出章纲再写正文）→ 本地过审自检（去 AI 味）→ 一键导出 5 种格式`。

### 2. 面向什么用户

| 用户群 | 特征 | 是否被服务好 |
|---|---|---|
| **中文网文连载作者**（主力） | 日更、几十万字、多平台投稿、怕 AI 率检测 | 功能最全，但上手门槛高 |
| 兴趣写作 / 个人创作者 | 想写但怕麻烦、非技术背景 | 安装是硬门槛，容易流失 |
| 靠小说赚钱的创作者 | 关心过审、排版、批量 | 「去 AI 味 + 分章导出」正中需求 |
| 开发者 / 自托管爱好者 | 关心隐私、本地优先 | 强契合（SQLite 零配置） |

### 3. 当前核心功能

- **分层记忆引擎**：近 4 章全文 + 近 3 章摘要 + AI 远楼层压缩，解决"写长降智"。
- **设定管线（自动填表）**：每章生成后抽人物/地点/势力 → 自动建角色卡与世界书词条 → 检测关系 → 回写故事线。
- **探讨模式 11 步 + 缝合怪推进**：从一句话到完整世界观；主线完结自动接新线（快/均衡/慢热三档）。
- **本地过审自检（humanize）**：`src/core/humanize/`（rules.ts 23KB + index.ts 7KB），纯规则引擎、
  **零 LLM 调用、零联网、零成本**，给段落级「AI 味」绿/黄/红评分 + 命中原因 + 改法建议。
- **批量写作两段流**：一次 1-10 章，先出章纲改，确认后后台逐章写。
- **可信赖三件套**：失败说人话（v3.1.70/82/83）、三层自动保存（v3.1.76）、正文乐观锁（v3.1.84）。
- **拆书 / 仿写 / 创意工坊预设 / 关系图 / 全文检索 / 章内查找替换**。

### 4. 技术架构

- Next.js 16.3.3 (App Router) + React 19 + TypeScript 5，Turbopack 开发 / Webpack 生产。
- Tailwind CSS v4（虚空玻璃设计系统）+ Zustand 状态管理。
- **Prisma 7 + better-sqlite3 本地文件库**（`./data/novelforge.db`），27 个 model，无 Docker / 无 Postgres / 无云端。
- 130+ API Route，生成走 SSE 流式（`src/core/write-generation.ts` → `runWriteGeneration`）。
- 多 LLM 提供商（OpenAI 兼容协议），Key 存本地 SQLite。
- 工程质量扎实：vitest 1529 测试全绿、tsc 0 错、CI 通过、有快照回滚体系（`scripts/git-snapshot.sh`）。

### 5. 已有优势（真正的护城河）

1. **本地优先 + 隐私零顾虑**：未发表稿件、API Key、设定全在本机。这是云端竞品（NovelAI / 彩云小梦 /
   Sudowrite）**结构上做不到**的事，尤其对"怕平台偷稿/怕 AI 率检测"的网文作者是刚需。
2. **humanize 去 AI 味是 SEO 级磁石**：中文写作圈搜索量极大的需求；纯本地、不上传稿件，
   对比一切"必须上传未发表稿件才能检测"的云端 AI 检测服务，**是决定性差异**。
3. **长篇 × 中文 × 本地 × 全流程的四维交集**：竞品追单点容易，追四层要重写架构。
4. **工程质量远超同类个人项目**：1500+ 测试、乐观锁、自动保存、冲突面板、快照回滚——这是"敢托付心血"的信任底座。

## 二、真实用户视角：完整体验链路与流失点

以下按一个**从未听说过本项目的中文网文作者**的真实路径走一遍。

### Step 0 · 发现项目
- **路径**：GitHub 搜「AI 写小说 / 去 AI 味 / 本地写作」→ 或别人推荐 → 落到仓库主页。
- **摩擦点**：Topics 虽已铺 `humanize / ai-detection / privacy`，但仓库 **Star 只有 1**。
- **流失原因**：**社会认同缺失**。技术再好，"1 star"会让多数访客默认"没人用 = 可能不好用/会弃坑"，
  尤其作者要拿它写几十万字，最怕工具半路跑路。这一步的流失是**最大且最沉默**的。

### Step 1 · 读 README
- **路径**：看 banner → 定位语 → 「它解决什么问题」→ 核心亮点表 → 快速开始。
- **摩擦点**：
  - 第 20 行写着 **v3.1.60**（实际 3.1.92），README_EN 更旧（v3.1.57）。
  - 「在线预览」链接是旧域名，且明确告知"只能看界面、不能操作"。
  - 亮点表信息密度高但**缺少"我现在就能试"的钩子**。
- **流失原因**：版本号陈旧 → "维护不活跃？"；无法在线试用 → "装了才知道好不好，风险太高"。
  作者的时间成本高，不愿为陌生工具付"安装成本"。

### Step 2 · 决策：装还是不装
- **路径**：评估"装它值不值" → 关键看能否**先尝一口**。
- **摩擦点**：唯一无需 Key 就能产生价值的功能（去 AI 味检测）**没有被前置宣传**，
  用户此时并不知道"不配 Key 也能立刻用上真东西"。
- **流失原因**：**价值验证成本过高**。要看到价值必须先：装 Node → clone → install → 配 Key（还有钱的风险）。
  四步里任何一步卡住就放弃。这一步流失的用户**根本不会进 Issue**，所以你看不到。

### Step 3 · clone 与安装
- **路径**：`git clone` → `npm install` → `npm run dev:db`。
- **摩擦点**：
  - `better-sqlite3` 是原生模块，Windows 上预编译包偶发缺失（历史踩过：需手动从 GitHub releases
    下 `node-v127-win32-x64` 预编译包塞进 `node_modules/better-sqlite3/lib/binding/`）。
  - 安装失败时**没有任何兜底指引**，README 也没提这个已知坑。
- **流失原因**：非技术作者卡在编译错误 → 无从下手 → 直接放弃。

### Step 4 · 首次启动
- **路径**：打开 `http://localhost:3001` → 首页空态。
- **摩擦点**：
  - 空态有引导（"还没有小说项目，挑一种方式开始你的故事"）和「一键载入示例项目（仙侠）」，**这块做得不错**。
  - 但顶部横幅（AI 未配置）会立刻弹"AI 未配置"警告，**新用户还没开始就被拦一道**.
  - 若数据库没起来，横幅让用户跑 `docker compose up -d`（S2）—— **项目根本不用 Docker**，
    用户会以为"这项目要装 Docker"而直接放弃，或装了 Docker 也解决不了问题。
- **流失原因**：**首启动即被误导 + 被警告**。第一印象是"这东西没配好不能用"。

### Step 5 · 配置 LLM（最大门槛）
- **路径**：设置页 → 选提供商 → 填 Key → 测试连接 → 保存。
- **摩擦点**：
  - 设置页本身做得清晰（分 1/2 步、有「测试连接」、未填 Key 有明确提示），**这块合格**。
  - 但**门槛本质没消除**：用户得先去注册硅基流动/DeepSeek、实名、充值。对"只是想试试"的人是硬门槛。
- **流失原因**：**付费与注册门槛**。大量潜在用户在这一步流失，且不可逆。

### Step 6 · 跑通第一个用例
- **路径**：探讨模式聊世界观 → 采纳建档 → 工作台 → 生成章节。
- **摩擦点**：
  - 路径长（探讨 → 采纳 → 建项目 → 工作台 → 生成），中间任一步 AI 返回不佳就会卡住。
  - 有「下一步建议」引导（v3.1.62）和示例项目，缓解了一部分。
- **流失原因**：**首次成功来得太晚**。用户在看到第一个像样的成果前，已经投入了 30+ 分钟和真金白银的 token。

### Step 7 · 遇到问题求助
- **路径**：出错了 → 找帮助。
- **摩擦点**：
  - 有 `ISSUE_TEMPLATE`（bug_report / feature_request / config）和 PR 模板，**但 Issue 数是 0**。
  - 没有 `CONTRIBUTING.md`，没有 Discussions（未启用），没有 FAQ / 常见问题页。
  - 报错虽然"说人话"了（v3.1.70/82/83），但**没有自助排查清单**（如 better-sqlite3 编译失败怎么办）。
- **流失原因**：**求助无门**。用户卡住时如果不问（多数人不问），就静默流失；想问也不知道该给什么信息。

### Step 8 · 反馈与贡献
- **摩擦点**：无贡献指南、无 Discussions、Star 1（无认同感）。
- **流失原因**：**从"使用者"到"传播者"的转化路径不存在**。用过觉得好的人，没有低成本的"支持一下"入口。

## 三、升级计划

### 3.0 取舍原则（先说剔除什么）

**明确剔除（不做）**：
- ❌ 依赖升级（eslint 9→10、dependabot PR）—— 用户不可感，且当前有兼容性阻塞。
- ❌ 纯代码重构 / 架构调整 —— 无用户可感收益。
- ❌ 无实质改进的版本号堆叠 —— 只会制造噪声。
- ❌ 插件 API、双语文档站、移动端响应式 —— 太远，当前阶段不产生 Star。
- ❌ 游戏模式投入 —— ROADMAP 已判定降级为卫星功能，正确。

**保留原则**：每条改进必须能回答——**它让哪类用户更少地放弃，或更愿意点 Star？**

---

### 3.1 速赢项（低成本 · 高收益 · 1 周内）

#### A1 · 修掉「Docker 幽灵」提示（首启动致命误导）
- **目标用户**：所有 clone 后首次启动的新用户（尤其非技术作者）。
- **解决痛点**：数据库报错/未连接时，界面让用户去跑 `docker compose up -d`——但项目自 v3.1.42 起
  已彻底移除 Docker 与 Postgres，这条提示会把用户引向死路，是**首启动第一大劝退点**。
- **预期收益**：新用户首次启动成功率提升；不再出现"装了 Docker 也没用"的困惑。
- **验证方式**：故意让 `data/novelforge.db` 不可写 → 触发 DB 错误 → 确认提示文案为
  「运行 `npm run dev:db`（或 `npx prisma db push`）重建本地数据库」，且**不再出现 docker 字样**。
- **成本**：**低**（改 3 处文案 + 1 处测试断言）。
- **排期**：**第 1 周，立即做**。
- **具体改动点**：
  1. `src/lib/api-error.ts:30` — hint 从「请确认 PostgreSQL 已启动（本地用 `docker compose up -d`）…」
     改为 SQLite 时代正确指引（检查 `./data/` 是否可写 → 跑 `npm run dev:db`）。
  2. `src/components/system-status-banner.tsx:33` — `DB_FIX_CMD` 从
     `"docker compose up -d && npx prisma db push"` 改为 `"npm run dev:db"`。
  3. `src/lib/api-error.test.ts:17` — 断言从 `toContain("docker compose")` 改为
     `toContain("npm run dev:db")`（**必须同步改，否则测试固化错误行为**）。
  4. 全库再 grep 一次 `docker compose`（排除 `changelog-data.ts` 历史记录），确认业务代码零残留。

#### A2 · README 版本号对齐 + 自动同步（防复发）
- **目标用户**：所有 GitHub 访客（Star 决策发生在读 README 的前 30 秒）。
- **解决痛点**：README 写 v3.1.60、英文写 v3.1.57、实际 v3.1.92——访客第一印象是"落后 32 个版本、
  维护不活跃"，直接压低 Star 意愿。
- **预期收益**：首印象可信度恢复；且以后不会再漂。
- **验证方式**：`grep "当前版本" README.md` 与 `node -p "require('./package.json').version"` 一致；
  跑一次 `node scripts/bump-version.js` 后 README 版本行自动跟着变。
- **成本**：**低**（改 2 行 + 脚本加 ~10 行）。
- **排期**：**第 1 周**。
- **具体改动点**：
  1. `README.md:20` — `v3.1.60` → `v3.1.92`。
  2. `README_EN.md:17` — `v3.1.57` → `v3.1.92`（顺带把英文简介补到与中文一致的卖点密度）。
  3. `scripts/bump-version.js` — 在写 `changelog-data.ts` 之后，增加"正则替换 README.md 与
     README_EN.md 的版本行"步骤，使版本同步成为流程的一部分（根治 S5）。

#### A3 · 改名遗留清理
- **目标用户**：所有访客 / 开发者。
- **解决痛点**：`novel-forge` → `novel-smith` 改名后仍有残留，显得项目不一致、不用心。
- **预期收益**：品牌一致性；细节好感。
- **验证方式**：`grep -rn "Novel Forge" .env.example README.md src/` → 业务代码零命中（历史 changelog 除外）。
- **成本**：**低**。
- **排期**：**第 1 周**（与 A1/A2 同批提交）。
- **具体改动点**：
  1. `.env.example:1` — `# Novel Forge 环境变量模板` → `# Novel Smith 环境变量模板`。
  2. `README.md:5` 预览徽章与 `:18` 预览链接 — 旧域名 `novel-forge-nu.vercel.app` → 新域名
     （需先在 Vercel 改名，若暂不能改则在 README 明确标注"演示站为只读预览"）。

#### A4 · 首页空态补位 + 前置「零门槛体验」入口
- **目标用户**：首次打开的新用户。
- **解决痛点**：3 列 grid 只放 2 张卡（`src/app/page.tsx:254-257`），首屏空一块；
  且空态里**没有指向"不配 Key 也能用"功能的入口**。
- **预期收益**：首屏引导完整；把新用户导向零门槛的"哇塞时刻"（配合 B1）。
- **验证方式**：清空项目后打开首页，空态为 3 张饱满卡片，其中一张直接指向去 AI 味检测页。
- **成本**：**低**（加 1 张 FeatureCard + 1 条路由链接）。
- **排期**：**第 2 周**（依赖 B1 落地）●
- **具体改动点**：
  1. `src/app/page.tsx:254-257` — 在 `FeatureCard` 网格中补第三张卡（去 AI 味检测，`href="/detector"`）。
  2. 首页顶部导航或 hero 区加入口链接，让**已有项目的老用户**也能一键找到。

### 3.2 决定项目上限的长期项

#### B1 · 【最大杠杆】零门槛首体验页 `/detector`：不配 Key 也能惊艳
- **目标用户**：**所有还没配 Key 的潜在用户**（这是当前流失最惨的一步）。
- **解决痛点**：项目最强的差异化（本地去 AI 味）被埋在"配 Key + 建项目 + 写章节"三道门之后。
  而 `analyzeText()` 是**纯函数、零 LLM 调用**（`src/core/humanize/index.ts:47`，已 grep 确认
  `src/core/humanize/` 内无任何 `completeText`/`fetch` 调用）——它**根本不需要 Key、不需要数据库、不需要项目**。
- **做什么**：新建一个独立页面 `/detector`：粘贴（或直接试用示例文本）任意一段文字 → 立刻得到
  段落级绿/黄/红评分 + 命中原因 + 改法建议。全程纯前端、零联网、零成本。
- **预期收益**：
  - 新用户 clone 后 **30 秒内**获得第一次"哇，这东西真有用"——把"价值验证"从 30 分钟压缩到 30 秒。
  - 直接把最强卖点变成 Star 磁石（对应 ROADMAP「第 1–2 周 Star 破 10」目标）。
  - 天然可传播：作者会把它当"投稿前自检工具"推荐给同行——**这是 Star 的自增长飞轮**。
- **验证方式**：新装环境、断网、不填 Key → 访问 `/detector` → 粘贴一段 AI 腔文本 → 能出分、能高亮、
  能给改法建议；且 `/api/health` 显示 llm 未配置也不影响本页。
- **成本**：**中**（新页面 + 复用展示逻辑 + 少量单测 + 文档）。**收益/成本比最高的一项**。
- **排期**：**第 2–3 周**（A 组速赢项之后的第一个重点）。
- **具体改动点**：
  1. 新建 `src/app/detector/page.tsx` — 客户端组件，直接 `import { analyzeText } from "@/core/humanize"`
     （纯函数，可在客户端跑），输入区 + 结果区，**不依赖任何 API 路由、不依赖 prisma**。
  2. 复用 `src/components/workspace/HumanizePanel.tsx` 的展示逻辑（段落色条 / 命中高亮 / 严重度筛选）——
     建议把展示部分抽成可复用组件，供写作台与新页面共用，避免两套 UI。
  3. `README.md` — 新增「零门槛试用」章节，**放在快速开始之前**："不想配 Key？clone 完直接打开
     `/detector`，粘贴一段文字，立刻看它有多像 AI 写的——全程在你电脑上，不联网。"
  4. 补少量单测（页面级 smoke + analyzeText 边界：空文本 / 超短文本 / 超长文本）。
  5. 顶部 `SystemStatusBanner` 需排除 `/detector` 路径的"AI 未配置"告警（该页本就不需要 Key，
     否则一进页面就被黄条警告，抵消零门槛效果）。

#### B2 · 首启动向导：把"先给甜头、再要 Key"变成流程
- **目标用户**：首次打开的新用户。
- **解决痛点**：现在一进门就被"AI 未配置"黄条警告，第一印象是"没配好不能用"。
- **做什么**：首次访问（localStorage 无标记）时展示 3 步引导：
  ① 先试试去 AI 味检测（**无需 Key，30 秒**）→ ② 一键载入示例项目看看长什么样 → ③ 配好 Key 开始写作。
- **预期收益**：把"先付出（配 Key）再得到价值"反转为"先得到价值再付出"，显著降低 Step 5 流失。
- **验证方式**：清 localStorage → 打开首页 → 引导按序出现，第 1 步可跳过 Key 直接完成。
- **成本**：**中**。
- **排期**：**第 4–5 周**。
- **具体改动点**：
  1. 新建 `src/components/FirstRunGuide.tsx`（可关闭、localStorage 记住）。
  2. `src/app/page.tsx` 挂载；步骤 ① 跳转 `/detector`，② 复用现有 `loadSample`，③ 跳转 `/settings`。
  3. `src/components/system-status-banner.tsx` — 首启动未完成引导前不弹"AI 未配置"（改为引导内提示）。

#### B3 · 社区基建：让"想支持一下"变成低成本动作

- **解决痛点**：无 `CONTRIBUTING.md`、无 Discussions、Issue 0、Star 1——**没有社会认同，也没有贡献入口**。
- **预期收益**：降低贡献门槛 → Issue/PR 增加 → 仓库活跃度提升 → 正向影响 Star。
- **验证方式**：仓库出现 CONTRIBUTING.md；Discussions 已开启；README 有明确"如何参与"三步。
- **成本**：**低—中**（主要是文档与仓库设置）。

### 3.4 优先级排序与取舍理由

**排序（建议执行顺序）**：

1. **A1（Docker 幽灵提示）** — 它是**正在主动伤害每一个新用户**的错误，且修复只要改 3 行。
   没有任何理由不第一个做。
2. **A2 + A3（版本号/改名清理）** — 直接作用于"读 README 的前 30 秒"，而 Star 决策就发生在那里。
   成本极低，收益直接。
3. **B1（零门槛 `/detector`）** — **决定项目上限的一项**。理由：当前最大的结构性问题是
   "价值被 Key 墙挡住"，而项目恰好有一个**不需要 Key 的杀手锏**。把它前置，等于把获客漏斗
   从"装好 → 配 Key → 才看到价值"改成"装好 → 立刻看到价值 → 自愿去配 Key"。这是唯一一个
   能同时提升"好感度 + 传播性 + Star 意愿"的改动。放在 A 组之后，因为它需要新页面（成本中）。
4. **B3 + B4（社区基建 / 英文 README）** — 打开增量渠道，成本低，可与 B1 并行。
5. **B2（首启动向导）** — 锦上添花，依赖 B1 存在才有意义，排最后。

**取舍理由总结**：
- 先修**正在伤人的**（A1），再修**影响第一印象的**（A2/A3），然后做**决定上限的**（B1），
  最后做**放大渠道的**（B3/B4）和**体验润色的**（B2）。
- 一切都围绕一个问题：**"这一步让谁更不容易放弃？"** 答不上来的就不做。
