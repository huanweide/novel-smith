# 核心架构模式——记忆系统、章节工作流、调度引擎

> 提取自完整架构文档，剥离具体例子，只保留可复用的架构模式。

## 一、章节创建五阶段工作流

```
阶段一：创建大纲节点（1次工具调用）
  outline_create → outline_nodes 表新增记录
  返回：节点ID，摘要为空

阶段二：自由讨论生成章纲（多轮对话 + 并行查询）
  并行加载：大纲树 + 角色 + 伏笔 + 主线 + 支线 + 事件历史
  AI 分析现状 → 用户提方向 → 多轮细化 → 可选创建新角色/伏笔

阶段三：保存章纲（1次工具调用）
  outline_update → 写入摘要字段

阶段四：生成正文（1次核心调用，内部自动完成大量工作）
  chapter_generate_content 内部：
    自动检查章节是否存在 → 不存在则自动创建
    六类来源并行加载：
      来源1：记忆注入（待兑现事项 + 主角状态档案 + 分层故事回顾 + 写作备忘录）
      来源2：上下文窗口（前3章摘要 + 后1章大纲 + 前10章事件线 + 前5章支线流）
      来源3：实体数据（角色/物品/伏笔/势力/地点）
      来源4：风格控制（文风/对话/描写密度/节奏偏好）
    组装提示词 → 发送大模型 → 流式返回 → 写作面板渲染

阶段五：后处理（蒸馏引擎自动运行，1-3秒）
  实体检测 → 状态更新 → 伏笔管理 → 事件提取 → 时间线更新 → 待兑现检查
```

**关键设计决策：**
- `chapter_generate_content` 是唯一的核心枢纽——一次性加载所有数据，一次 API 调用完成
- 用户只需参与"讨论章纲"和"采纳正文"两个环节，其余全自动化
- 每次从数据库重新拉取最新数据，不依赖对话历史中的旧版本

## 二、记忆系统三层架构

```
第1层：工作记忆（Working Memory）
  内容：当前对话上下文 + 最新工具调用结果 + 用户最新指令
  存储：session 表 + conversation_context 表
  生命周期：当前对话结束即消失
  容量：~8000 token

第2层：短期记忆（Short-term Memory）
  内容：最近3-5章摘要 + 最近10章事件线 + 最近5章支线状态 + 写作习惯统计
  存储：chapter_summaries 表 + writing_habits 表
  生命周期：跨对话保持，随着新章节覆盖旧数据
  容量：按章节数滚动

第3层：长期记忆（Long-term Memory）
  内容：所有角色完整档案 + 完整伏笔链 + 完整世界观 + 完整时间线 + 全部物品/功法/势力
  存储：各业务表（characters, foreshadows, worldview, timeline, items, factions...）
  生命周期：永久保存
  容量：无上限
```

**记忆写入流程（蒸馏引擎）：**
```
用户采纳正文
  → 实体检测（正则 + NER）
  → 状态更新（对比前后差异）
  → 伏笔管理（检测回收/深化/新埋设）
  → 事件提取（按重要性分级）
  → 时间线更新
  → 待兑现事项更新
  → 写入各业务表（第2层 + 第3层）
```

**记忆读取流程（写正文时）：**
```
chapter_generate_content 启动
  → 第1步：确定目标（当前大纲节点 + 章节序号）
  → 第2步：加载记忆注入（待兑现 + 主角档案 + 故事回顾 + 备忘录）
  → 第3步：加载上下文（前3章摘要 + 事件线 + 支线流）
  → 第4步：加载实体数据（角色 + 物品 + 伏笔 + 势力 + 地点）
  → 第5步：组装提示词（格式化所有数据 + 风格控制 + 用户指令）
  → 第6步：发送大模型 → 返回正文
```

## 三、时间线感知过滤器（最关键的设计）

**核心问题：** 用户跳章写（先写第10章再写第7章）时，第10章的修为变化不能污染第7章的上下文。

**解决方案：按章节时间线过滤记忆，不是按写作时间线。**

```
写第N章时的过滤规则：
  ├── 角色状态：只取第1章到第N-1章之间的状态变化
  ├── 伏笔状态：只取"埋设时间 < N"的伏笔
  ├── 物品归属：只取第1章到第N-1章之间的归属变化
  ├── 事件线：只取第1章到第N-1章之间的事件
  └── 待兑现事项：只取"deadline_chapter >= N"的项
```

**四种写作路线的不同处理：**

| 路线 | 关键差异 |
|------|---------|
| 正常写（有序） | 全量加载前N-1章状态 |
| 续写 | 额外加载本章已有的最后500字作为续写起点 |
| 跳章写 | 按章节序号过滤，未来章节的状态不可见 |
| 改大纲后写 | 从数据库重读最新大纲，不依赖对话中的旧版本 |
| 自由写作 | 正常加载约束，但蒸馏引擎更激进地创建新实体 |

## 四、Agent 工具调度系统

**核心问题：** 用户一句话可能触发多个工具，需要确定调用顺序和并行策略。

**架构：依赖图 + 并行优化**

```
工具依赖关系：
  chapter_generate_content → depends_on [character_query, foreshadow_query, outline_query, worldview_query]
                             → 这些依赖可并行执行（都是只读查询）
  
  character_update → depends_on [character_query]（先查再改，不可并行）

并行组（可同时调用的工具）：
  [character_query, foreshadow_query, outline_query, worldview_query, faction_query, geo_map_query]
  → 这些是纯查询，无相互依赖

调度策略：
  阶段1：并行执行所有无依赖的工具
  阶段2：串行执行有依赖链的工具
  错误处理：必需工具失败 → 整体失败；可选工具失败 → 忽略继续
```

**意图解析：关键词 → 工具映射**
```
"分析" → [chapter_content_query, character_query, foreshadow_query, plot_line_query]
"写"   → [chapter_generate_content]
"修改" → [character_update, outline_update, chapter_update]
"查询" → [character_query, foreshadow_query, outline_query]
"创建" → [character_create, faction_create, item_create]
```

## 五、蒸馏引擎架构（不调大模型 API）

### 新实体检测——命名模式库

核心不是代码，是**对中文仙侠命名规则的领域知识**：

```
丹药模式：r'[一二三四五六七八九十]品[一-鿿]{2,4}丹'
法宝模式：r'[一-鿿]{1,3}(?:剑|刀|镜|鼎|塔|印|旗|幡|珠|环|镯|簪)'
功法模式：r'[一-鿿]{2,6}(?:诀|经|典|功|法|术|引|咒|拳|掌|指|腿)'
地点模式：r'[一-鿿]{2,4}(?:山脉|山谷|峡谷|城|镇|村|宗|门|派|殿|阁|洞|府|宫)'
材料模式：r'[一-鿿]{2,4}(?:草|花|果|叶|根|藤|石|木|玉|晶|矿|铁|铜)'
```

**排除词库（防误报）：** 身体部位（拳头/手掌/膝盖）、普通名词（桌子/茶杯/纸张）

### 归属推断——三层策略

```
策略1：属格匹配 "XX的XX" → 置信度 0.95
策略2：动词前置 "XX从储物袋中取出XX" → 置信度 0.85
策略3：段落主人推断（段落中频率最高的角色）→ 置信度 0.6
无法推断 → 标记为"不确定"，留待用户确认
```

### 消歧——同名不同物

```
同名实体通过三个特征区分：
  特征1：上下文中的角色不同（"苏月瑶的玉佩" vs "掌柜的玉佩"）
  特征2：修饰词不同（"手中握着的" vs "柜台里的"）
  特征3：动词不同（"握紧" vs "标价"）
```

### 伏笔检测——触发词 + 模式匹配

```
埋设信号：["他并不知道", "谁也没有注意到", "冥冥之中", "神秘的XX", "似乎隐藏"]
回收信号：["原来", "真相", "果然", "正如", "终于明白", "恍然大悟", "原来如此"]
深化信号：关键词再次出现但无回收标记词 → 默认为深化
```

### 重要性评分——六维权重

| 维度 | 权重 | 逻辑 |
|------|------|------|
| 出现频率 | 最多50分 | 出现越多次越重要 |
| 出现位置 | 20-30分 | 结尾 > 开头 > 中间 |
| 修饰词强度 | 15分/词 | "神秘""古老""惊天""绝世" |
| 与已有伏笔关联 | 40分 | 直接关联伏笔的实体最重要 |
| 实体类型权重 | 15-30分 | 角色30 > 事件25 > 物品20 > 地点15 |
| 与主角关联度 | 25分 | 主角相关的优先级高 |

## 六、提示词分层规则系统

```
第1层：身份定义（语气最正式）
  "你是 AI 小说家的智能助手（Agent 模式）。"

第2层：硬规则（★★★ 标记，命令式语气）
  "必须" / "禁止" / "严禁" / "违反会出严重问题"

第3层：中等规则（★ 标记，建议式语气）
  "建议" / "可以" / "优先"

第4层：动态上下文（当前项目状态）
  项目名称、当前编辑章节

第5层：工具说明（JSON Schema 格式）
  每个工具的参数和返回值
```

**关键设计：** 硬规则用符号标记（★★★），模型对视觉标记比纯文本更敏感。硬规则用"必须/禁止"，中等规则用"建议/可以"。

## 七、并发安全的状态管理

**核心问题：** 用户在前端操作 + Agent 在查询，可能同时修改同一数据。

**方案：乐观锁 + 版本号**

```
读取时：SELECT *, version FROM {table} WHERE id = ?
写入时：UPDATE {table} SET ..., version = version + 1
        WHERE id = ? AND version = ?  ← 版本不匹配则拒绝
```

## 八、整体架构的核心哲学

1. **一次性加载，一次调用，流式返回**：上下文只构建一次，全章一次生成，Token 只消耗一次
2. **蒸馏不调 API**：本地正则/NER/关键词/状态对比，1-3秒完成，零 API 消耗
3. **时间线感知**：跳章写时不污染上下文，按章节序号过滤记忆
4. **按需加载，用完即弃**：数据只在需要时从数据库加载，不常驻上下文
5. **数据库是唯一真相源**：Agent 每次从数据库重读最新数据，不依赖对话缓存
6. **最难的不是代码，是领域规则**：命名模式库、消歧策略、伏笔触发词——这些是中文网文领域的专业知识
