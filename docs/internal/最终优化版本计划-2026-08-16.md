## 二、实测暴露的问题（按优先级排序）

### 🔴 P0 — `globalPrompt` 已膨胀到 18 万字，每次生成全量注入
- **现象**：实测后 `Project.globalPrompt` 长度 **181,574 字符（≈18万 token）**。
- **为什么是大问题**：`CONTEXT_WINDOW_SIZE=131072`，每次生成把 18 万字全拼进 system prompt，**超出上下文窗口** → 要么被截断丢真上下文，要么硬撑导致输入 token 爆炸。这直接拉慢速率、烧钱、且可能让模型忽略真正相关的设定。
- **这是"单章速率慢"的头号元凶**（见 P1-3）。

### 🟠 P1 — 进度可视化是"章级粗粒度"，让人干等
- **现象**：模式B写 3 章时，进度条 **0% 持续约 3 分钟**才突然跳到 33%，再 3 分钟跳 67%。
- **为什么不好**：你明确要求"后台运行且进度可视化、不要让人等很久"。现在 0% 一挂 3 分钟，用户会以为卡死。

### 🟠 P1 — 单章生成速率偏慢（≈206 秒/章）
- **实测**：3 章正文平均 **206.2s/章**，单章 ~2500–2900 中文字，约 **12.7 字/秒（≈760 字/分）**。
- **根因**：主要是 P0 的 18 万 token 输入拖累；其次流式写入 + Neon 数据库逐字往返。DeepSeek-V4-Flash 本身不慢，是被输入拖死。

### 🟡 P2 — 剧情校准 HUD 格式不一致
- **现象**：第9、11章有「【剧情校准 HUD】」块，第10章没有。
- **为什么不好**：同一本书里格式忽有忽无，长篇读感割裂。属于"文本一致性"缺口。

### 🟡 P2 — 批量流缺"该确认处确认"的中间闸门
- **现象**：模式A 建章+章纲后直接进模式B 写正文，没有"章纲确认/可编辑再写"的停留点。你要求"该确认的地方有确认"。
- **已有能力可复用**：v1.8.17 的"摘要大纲确认"机制 + v2.0.1 的 `digest-aggregate` 纯函数。

### ⚪ P3 — 环境与启动两个坑（已踩并已记进项目记忆）
- 配置源 `AppSettings`（DB）**优先于** `.env`，只改 `.env` 不生效（之前误改 `.env` 白忙）。
- dev server **必须用 `npm run dev`**；直调 `next dev` 会导致所有 `/api/*` 路由 404。
- 这两点不修代码，写进文档/记忆防复发即可。

## 三、优化路线图（分版本，具体可落地）

### 🎯 v2.51.x — 砍掉输入膨胀 + 进度从"章级"变"字级"
**目标：单章速率从 ~206s 降到 ~40–60s，进度条实时走动。**

**① globalPrompt 聚合摘要（解决 P0，最关键）**
- **为什么**：18万 token 输入是速率/成本头号杀手，且超窗口。
- **怎么做**：复用 v2.0.1 的 `digest-aggregate` 纯函数思路，新增 `buildCompactPrompt(project)`：
  - 世界卡/角色卡/规则先过"去重 + 垃圾过滤 + 标题归一"（同 digest-aggregate 逻辑）；
  - 压成**精简版全局设定（目标 < 8K token）**作为常驻 system 上下文；
  - 再按"当前章节节点"**按需注入**：只拼「本章出场角色卡 + 相关世界卡 + 适用规则」，而非全量。
  - 长设定支持分块检索：用章节关键词从设定库捞相关片段注入。
- **可行性**：中。Project 已有 `worldCards/characterCards/rules` 结构化字段可关联检索；`digest-aggregate` 纯函数现成可抄。改动集中在 `src/core/llm` 的 prompt 拼装处。

**② 字级流式进度（解决 P1 进度）**
- **为什么**：0% 挂 3 分钟像卡死。
- **怎么做**：`/api/generate/write` 的 SSE 流里，每个 token 批次回调上报 `generatedChars`；前端进度 = `章进度×0.7 + 字数进度×0.3`，并实时显示"已生成 X 字 / 目标 Y 字"。
- **可行性**：小。`write` 路由本就是 SSE 流式、已有逐字写入，加一个计数回调即可。

### 🎯 v2.52.x — 速率再榨 + 文本一致性
**③ 首字时间与并发优化（深化 P1-3）**
- 章纲生成本就并行（模式A 三章同时跑），正文也可探索"章内分段并发"或提高流式首字响应；
- `MAX_TOKENS_PER_REQUEST` 与 `CONTEXT_WINDOW_SIZE` 在 V4-Flash 上建议 `131072 / 8192` 维持，靠 ① 的输入裁剪见效最大。

**④ 剧情校准 HUD 格式开关（解决 P2）**
- 文风卡加字段 `hudMode ∈ {none, compact, full}`；
- 生成提示词据此约束（要就统一有、不要就禁）；或加一条正则后处理规则「禁止 `【剧情校准 HUD】` 残留」一键关。
- 可行性：小。

### 🎯 v2.53.x — 确认闸门 + 创意工坊增强
**⑤ 批量流"章纲确认"中间闸门（解决 P2 确认）**
- 模式A 返回 outlines 后**不自动进模式B**，前端展示章纲让用户确认/微调，再手动触发模式B 写正文；
- 复用 v1.8.17 摘要确认 UI，把"自动续写"变成"确认后续写"。
- 可行性：中。

**⑥ 创意工坊套用增强**
- 套用前预览"将改动/新增哪些卡"；同名卡冲突给「合并 / 覆盖 / 跳过」三选一，避免误覆盖项目原卡（本次实测 apply 文风预设会直接 upsert 成项目卡）。

## 五、P0 落地记录（v2.52.0 已完成，2026-08-16）

### 实测反推：优化前有「两个」速率杀手，不是「一个」
- 第一次 e2e（仅做 globalPrompt 压缩 + 字级进度后）单章仍 222 秒，且进度卡 99% 不完成——拆解时间线发现：
  - 写前准备 ~56s（上下文加载 + `planChapterStoryline` 1 次 LLM 剧情规划）：进度预置 3% 顶着；
  - 真·流式写作仅 ~25s（56→81s，3251 字）：globalPrompt 压缩后 AI 生成已很快；
  - **后置富化管线 ~141s（81→222s）**：`runPostGenerationPipeline` 串行跑 2 次 LLM 调用（审校 `reviewContent` + 摘要 `summarizeChapter` 含 3 次重试）+ 摘要素材重建/分类/冲突检测，把进度条卡在 99% 像死机。
- **结论**：globalPrompt 压缩解决了「生成慢」，但暴露了「富化阻塞交付」这个更大的体验坑。

### 三连击全部落地（commit 0258433 → origin main）
1. **globalPrompt 聚合摘要**：181574 → 12021 字符（15.1x），角色卡核心字段保真，配套 5 例单测。
2. **字级流式进度**：按「已生成字数/目标字数」实时回写 FillTask.progress，预置 3% + 下限 5% 防回跳。
3. **后置富化后台化（计划外新增，P0 实质收口）**：新增 `deferEnrichment` 开关——批量写作正文落库即 done，审校/摘要/伏笔/逻辑自查 fire-and-forget 后台跑；SSE 单章模式保持同步。真机复测单章 **222s → 91.3s（2.4x）**、进度平滑 100% 完成，不再卡 99%。
- 双门禁：tsc 0 错 / vitest 108 文件 1059 全绿。

### 路线微调建议
- **P1「速率再榨」改为主攻写前 ~56s 准备期**（而非再压生成）：可把 `planChapterStoryline` 与上下文构建并行化，或允许用户关掉「生成前剧情规划」换更快首字；这是剩余的最后一个可感知等待点。
- P2 两项（HUD 格式开关 / 章纲确认闸门）仍按原排期进 v2.52–v2.53，未阻塞。
