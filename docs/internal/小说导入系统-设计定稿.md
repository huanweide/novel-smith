# 小说导入系统（Import Novel）· 设计定稿

> **一句话定位**：导入不是「只读归档」，而是**带前史的建项目**——导入的每一章都是可写节点，随时可从任意章续写。
> **状态**：M1 已完成并通过 26 本真实语料验收（见第八节），M2 待启动。
> **关联**：拆书 `/dissect`、阅读器 `/read/[projectId]`、写作区 `/workspace/[projectId]`、角色卡、世界书、伏笔（PendingCommitment）全部复用，不新建管线。

---

## 一、核心模型：一个模型，两种用法

导入的章节**直接进现有 `StoryNode`**（写作区那套），不另开一张表。这样阅读器、章节 API、写作区全部天然复用，续写就等于「在导入的最后一章后面接一章」，零额外架构。

```
导入 ──> StoryNode 链 (type=chapter, source=imported)
              │
       ┌──────┴──────┐
   只读呈现层      可写编辑层
  （阅读器）      （写作区，续写节点 source=ai/user）
```

- 阅读器 = 呈现层；写作区 = 编辑层。**切换只改 UI，不搬数据**。
- `StoryNode` 新增 `source` 字段（`imported` / `ai` / `user`），保证续写内容不污染原始导入正文。

## 二、为什么必须支持续写（设计前提）

用户导入一本小说的典型动机有二：**(A) 只想读**；**(B) 读完想接着写/同人续写**。产品不能替用户猜死——所以默认姿态是**可读可续写**，只读只是"顺便也有"。

已否决的错误设计：把导入结果做成独立书架/只读归档表。代价是续写要重走建项目流程、白丢前史上下文，纯属自挖坑。

## 四、M1 统一中间格式

所有格式解析器**统一产出**：

```ts
type ParsedNovel = {
  title?: string;          // 书名（从文件名/元数据推断）
  chapters: ParsedChapter[];
  encoding?: string;       // 实际解码编码（仅 txt 有意义）
  warnings: string[];      // 解析告警（未识别章节、疑似乱码等）
};
type ParsedChapter = {
  index: number;           // 从 1 开始
  title: string;           // 章节标题
  content: string;         // 正文
  wordCount: number;
};
```

**分层解耦**：`解码（encoding）` → `抽纯文本（format）` → `切章节（splitter）` 三层独立，任一层可单独测试与替换。

- **编码层**：UTF-8 / UTF-8-BOM / GBK / GB18030 / Big5 嗅探，失败降级 + warning。国内 txt 乱码是最大痛点，必须一等公民。
- **格式层**：`txt` / `markdown` / `epub`（jszip + jsdom 已在依赖里，无需新增）。
- **切分层**：中文卷章识别器（第一章/第 1 章/卷一/序章/楔子/番外…）+ 英文 Chapter + 数字列表；正则可调 + 手动预览修正。

## 五、M1 CLI 先行（质量闸门）

先跑 CLI、不碰 UI，判据是**分章正确率**：

```bash
npm run import:dry <file>        # 打印切分结果 + 每章字数 + 置信度
npm run import:dry <file> --json # 机器可读，便于回归比对
```

用桌面上的**真实小说 txt** 迭代，分章正确率确认后再做 UI——避免 UI 写完才发现分章是错的、全部返工。

### 语料验收结果

26 本真实小说（txt + epub，含 GBK/GB18030/UTF-8-BOM），累计约 1.9 万章、5700 万字，
**分章全部正确**，仅 1 本（风姿物语 epub，644 章）留 1 条"卷末章偏短"提示，属正常。

### 过程中修掉的真 bug（都被测试固化）

| # | 问题 | 根因 | 影响 |
|---|---|---|---|
| 1 | 带 BOM 的 txt 一导入就抛异常 | 把可读名 `utf-8-bom` 直接喂 `TextDecoder`，Node 不认该标签 | **所有带 BOM 的 txt 全崩** |
| 2 | 「番外内容。」这类正文句被当标题，正文被吃掉 | 特殊篇名正则尾部过松，缺"句末标点 = 正文"防线 | **整章丢失** |
| 3 | epub 分出 0 字章、标题全是 `chapter N - 0` | epub 自带 spine 结构，却仍交给文本分章器猜 | 目录全是噪声 |
| 4 | 短章节被误判为目录页而丢失 | 目录判据只有"字数少且无句读"，正文只有一句话的章也会被杀 | **真章节丢失** |
| 5 | 健康度误报 99 章"偏短" | ① 用均值被大章抬高 ② 前置页/楔子/卷名页没豁免 | 假警淹没真问题 |

### 沉淀下来的四条判据（写代码时反复用到）

1. **编码先于分章**——顺序反了，后面所有识别器都在给乱码打工。
2. **结构化格式别再猜**——epub 有 spine，猜不如读；只有纯文本才需要分章器。
3. **异常检测用中位数不用均值**——均值会被离群章自己抬高/压低，两头都失效。
4. **告警要区分"真问题"和"书本来就这样"**——原书合并发布的超长章、卷末的短章、
   扉页人物表，都是正常形态，报出来只是噪音。真问题被噪音淹没，等于没报。
