# 小说导入系统（Import Novel）· 设计定稿

> **一句话定位**：导入不是「只读归档」，而是**带前史的建项目**——导入的每一章都是可写节点，随时可从任意章续写。
> **状态**：M1 已完成并通过 26 本真实语料验收（见第八节），M2 待启动。
> **关联**：拆书 `/dissect`、阅读器 `/read/[projectId]`、写作区 `/workspace/[projectId]`、角色卡、世界书、伏笔（PendingCommitment）全部复用，不新建管线。

---

## 一、核心模型：一个模型，两种用法

导入的章节**直接进现有 `StoryNode`**（写作区那套），不另开一张表。这样阅读器、章节 API、写作区全部天然复用，续写就等于「在导入的最后一章后面接一章」，零额外架构。

```
导入 ──> StoryNode 链 (type=chapter, source=imported)
              │
       ┌──────┴──────┐
   只读呈现层      可写编辑层
  （阅读器）      （写作区，续写节点 source=ai/user）
```

- 阅读器 = 呈现层；写作区 = 编辑层。**切换只改 UI，不搬数据**。
- `StoryNode` 新增 `source` 字段（`imported` / `ai` / `user`），保证续写内容不污染原始导入正文。

## 二、为什么必须支持续写（设计前提）

用户导入一本小说的典型动机有二：**(A) 只想读**；**(B) 读完想接着写/同人续写**。产品不能替用户猜死——所以默认姿态是**可读可续写**，只读只是"顺便也有"。

已否决的错误设计：把导入结果做成独立书架/只读归档表。代价是续写要重走建项目流程、白丢前史上下文，纯属自挖坑。

## 三、分期交付

| 期 | 目标 | 交付 |
|---|---|---|
| **M1** | 格式解析内核（地基） | 多格式解析 + 编码嗅探 + 中文章节识别 → 统一中间格式；**CLI 先行，分章正确率达标才碰 UI** |
| **M2** | 落库 + 续写闭环 | 导入进 `StoryNode`；阅读器复用 + "从此继续写"入口；目录/搜索一次性建索引 |
| **M3** | 前史资产自动提炼 | 角色卡/世界书/时间线/故事线/伏笔自动预填 → 喂给续写上下文 |
| **M4** | 三卡联动 + 体验收口 | 三卡一键从正文预填（复用拆书）；批量导入/格式记忆/导入报告 |

**格式优先级（已定）**：txt（含 GBK/GB18030 自动纠错）+ epub 打头；pdf/docx 靠后（PDF 解析脆、docx 需抽图）。

## 四、M1 统一中间格式

所有格式解析器**统一产出**：

```ts
type ParsedNovel = {
  title?: string;          // 书名（从文件名/元数据推断）
  chapters: ParsedChapter[];
  encoding?: string;       // 实际解码编码（仅 txt 有意义）
  warnings: string[];      // 解析告警（未识别章节、疑似乱码等）
};
type ParsedChapter = {
  index: number;           // 从 1 开始
  title: string;           // 章节标题
  content: string;         // 正文
  wordCount: number;
};
```

**分层解耦**：`解码（encoding）` → `抽纯文本（format）` → `切章节（splitter）` 三层独立，任一层可单独测试与替换。

- **编码层**：UTF-8 / UTF-8-BOM / GBK / GB18030 / Big5 嗅探，失败降级 + warning。国内 txt 乱码是最大痛点，必须一等公民。
- **格式层**：`txt` / `markdown` / `epub`（jszip + jsdom 已在依赖里，无需新增）。
- **切分层**：中文卷章识别器（第一章/第 1 章/卷一/序章/楔子/番外…）+ 英文 Chapter + 数字列表；正则可调 + 手动预览修正。

## 五、M1 CLI 先行（质量闸门）

先跑 CLI、不碰 UI，判据是**分章正确率**：

```bash
npm run import:dry <file>        # 打印切分结果 + 每章字数 + 置信度
npm run import:dry <file> --json # 机器可读，便于回归比对
```

用桌面上的**真实小说 txt** 迭代，分章正确率确认后再做 UI——避免 UI 写完才发现分章是错的、全部返工。

## 六、与现有能力的联动（M3/M4 的价值放大）

| 联动 | 作用 |
|---|---|
| 拆书 `/dissect` | 导入全文 → 出维度拆解 → 角色卡/世界观 |
| 角色卡 `CharacterCard` | 三卡自动预填（不手打），续写人物不失忆 |
| 世界书 `LorebookEntry` | 设定预填，续写世界观不崩 |
| 时间线/故事线 digest | 项目已有 `timelineDigest`/`storylineDigest`，续写知道讲到哪里 |
| 伏笔 `PendingCommitment` | 抽"埋了没收"的线成待兑现项，续写自动接着埋/收 |
| 仿写 `imitate` | 拿导入书文风生成风格卡 |

**导入的真正价值**：不是把已有功能列一遍，而是让**所有续写功能瞬间有素材**。

### 语料验收结果

26 本真实小说（txt + epub，含 GBK/GB18030/UTF-8-BOM），累计约 1.9 万章、5700 万字，
**分章全部正确**，仅 1 本（风姿物语 epub，644 章）留 1 条"卷末章偏短"提示，属正常。

### 过程中修掉的真 bug（都被测试固化）

| # | 问题 | 根因 | 影响 |
|---|---|---|---|
| 1 | 带 BOM 的 txt 一导入就抛异常 | 把可读名 `utf-8-bom` 直接喂 `TextDecoder`，Node 不认该标签 | **所有带 BOM 的 txt 全崩** |
| 2 | 「番外内容。」这类正文句被当标题，正文被吃掉 | 特殊篇名正则尾部过松，缺"句末标点 = 正文"防线 | **整章丢失** |
| 3 | epub 分出 0 字章、标题全是 `chapter N - 0` | epub 自带 spine 结构，却仍交给文本分章器猜 | 目录全是噪声 |
| 4 | 短章节被误判为目录页而丢失 | 目录判据只有"字数少且无句读"，正文只有一句话的章也会被杀 | **真章节丢失** |
| 5 | 健康度误报 99 章"偏短" | ① 用均值被大章抬高 ② 前置页/楔子/卷名页没豁免 | 假警淹没真问题 |

### 沉淀下来的四条判据（写代码时反复用到）

1. **编码先于分章**——顺序反了，后面所有识别器都在给乱码打工。
2. **结构化格式别再猜**——epub 有 spine，猜不如读；只有纯文本才需要分章器。
3. **异常检测用中位数不用均值**——均值会被离群章自己抬高/压低，两头都失效。
4. **告警要区分"真问题"和"书本来就这样"**——原书合并发布的超长章、卷末的短章、
   扉页人物表，都是正常形态，报出来只是噪音。真问题被噪音淹没，等于没报。

## 第九节 · M2–M4 交付记录（v3.1.145 – v3.1.147）

M1 解决「能不能读进来」，M2–M4 解决「读进来之后这东西到底有没有用」。

### 三个里程碑

| 版本 | 主题 | 一句话 |
|---|---|---|
| v3.1.145 | M2 落库 + 续写闭环 | 导入不再是只读归档，末尾一键接空白章接着写 |
| v3.1.146 | M3 前史资产自动提炼 | 导入后自动产出角色 / 设定 / 伏笔草稿与长期记忆摘要 |
| v3.1.147 | M4 三卡预填 + 批量 + 记忆 | AI 把草稿补成完整卡；多选批量导入；格式记忆 |

### 关键设计取舍

1. **导入节点直接进 `StoryNode` 链，不另建归档表。**
   另建「导入原文表」看着更干净，但那样导入的书永远进不了写作区，
   续写时上下文取不到它——为架构纯洁牺牲产品闭环是本末倒置。

2. **`source` 与 `importKind` 两组标记分离。**
   `source=imported|ai|user` 管「谁写的」（决定会不会被 AI 覆盖），
   `importKind=frontmatter|volume|chapter` 管「它是什么角色」（决定统计与展示）。
   合成一个字段就会在「卷名页也是导入的」这件事上自相矛盾。

3. **提炼零 LLM，预填才用 LLM。**
   提炼是「找出原文里明确写着的东西」，正则 + 统计足够且秒级、不烧钱；
   预填是「判断矛盾 / 驱动这类叙事特质」，只有 LLM 能做。
   两者混在一起会导致每次导入都产生 API 费用，慢到用户以为卡死。

4. **提炼产物一律 `reviewStatus=pending`。**
   `approved-cards.ts` 是所有生成端取用卡的唯一入口且硬过滤 `approved`，
   所以 pending 卡物理上不可能进生成上下文。这是唯一安全的落地方式——
   规则会误判路人甲，LLM 会编造设定，两者都不能直接放行。

5. **预填完仍保持 pending，`autoApprove` 默认关闭。**
   LLM 也会错。把「LLM 直接放行」做成默认，等于把安全闸交给概率。

6. **批量导入串行而非并发。**
   每本都是几百节点的写事务，并发只会加剧 SQLite 写锁争抢，
   且失败原因难归因。逐本进度可见，失败那本不影响其他本。

7. **上游 `entity-detector` 保持不动，清洗只在 M3 层做。**
   detector 的模式是「贪婪取 1~3 字 + 专名后缀」，天然会粘进量词与动词
   （`必须找到玄天鼎` → `到玄天鼎`、`柄青锋剑`）。改它会影响既有蒸馏与
   自动建卡的召回，代价远大于收益；在 M3 入口剥一层是更稳的边界。

### M3 提炼内核的采样取舍

一本 900 章的书正文几百万字，全量扫既慢又会把早期路过的路人甲也当角色。
默认取前 30 章 + 每 5 章采一章，且每章掐头去尾只取中段
（开头常是环境铺垫、结尾常是作者抒发，中段信息密度最高）。

| # | 问题 | 根因 | 影响 |
|---|---|---|---|
| 6 | chapters 接口对空 `request.url` 直接 500 | `new URL(request.url)` 无防御，测试传`{}` 即崩 | 3 个既有测试红 |
| 7 | Prisma 的 `array_contains` 在 SQLite 下不存在 | JSON 数组过滤写法是 Postgres 方言 | 草稿筛选与预填查询全报错 |

### 五条沉淀判据（M2–M4 复用）

1. **导入的终点不是「入库」，是「能接着写」。**
   一切设计都要问一句：这件事让作者离「写下一章」更近还是更远？

2. **规则填不了的字段就别填。**
   猜出来的矛盾、编出来的动机，一旦 approved 就是持续污染源。
   留空是可接受的中间态，编造不是。

3. **幂等键要用文件指纹，不用文件名。**
   同名文件可以是两本完全不同的书（不同版本、不同下卷）。

4. **批量不该降低单本的质量。**
   批量流程里仍然逐本走 preview → commit，不为了快而跳过体检。

5. **失败要降级，不要阻断。**
   提炼失败不该让已落库的正文作废——降级成 warning，作者事后可重跑。
